# 关联查询、多对多与三表案例

一对一、一对多是在**两张表**之间做文章；一旦关系变成"多对多"，就必然出现**第三张表**。本章沿着"学生 — 成绩 — 科目"三张表，把 `collection` 与 `association` 一层层套起来，直到把"某个学生每门课考了多少分"完整装配到内存里。

## 多对多的关系

源文对多对多的定义只有一句，但已经点明本质：

> 双向的一对多的关系，从任何一方看过去，它对应的对方都是"多"

也就是说，多对多不是一种新的数据库关系，而是**两个方向相反的一对多叠加**：一个学生考多门课，一门课有多个学生考。

**注意：因为是三张表，所有 sql 语句要使用到连接查询。**

### 为什么必须要有中间表

> [!info] 中间表（关联表）的作用
> 源文给出的"三张表"就是答案：`t_stu_info`（学生）与 `t_subject`（课程）之间并没有直接的外键，**真正的连接点在第三张表 `t_score`（成绩表）上**。
> `t_score` 同时持有两个外键：
> - `score_stu_id` → `REFERENCES t_stu_info(stu_id)`
> - `score_subject_id` → `REFERENCES t_subject(subject_id)`
>
> 一行成绩记录只表示"**某个学生**在**某门课**上的得分"，两个"多"就这样被拆成了两条一对多。因此任何一次多对多查询都必须**连上中间表**：先由学生找到成绩，再由成绩找到课程（或反方向走）。

### 连接查询复习（源文原文）

复习：内连接（普通内连接（针对多张表），自连接（针对一张表）），

内连接用的关键字 `inner join .....on`

***表名1的字段 = 表名2的字段：两张表的主外键关系***

```text
表名1 inner join  表名2  on 表名1的字段=表名2的字段
```

**内连接：取两张表的相同的数据**

外连接（左外连接，右外连接，全外连接），

**外连接：取两张表中一张表所有的数据，与另外一张表相匹配的数据**

交叉连接：两张表所有行的乘积的笛卡尔积的集合数据

a 表 4 条数据，b 表 3 条数据，一旦用了交叉连接，就会产生 12 条（4*3=12 条）

> [!tip] 连接方式与"要不要中间表"的关系
> 内连接只保留**两边都匹配得上**的记录，所以"从来没考过试的学生"会被丢掉；如果希望没成绩的学生也出现，就得改用左外连接。源文此处只做复习，本章的例子全部使用 `INNER JOIN`。

## 三表关联案例：学生、科目、成绩

> [!info] 源文标题层级说明
> 源文在"多对多的关系"之后，把"学生信息表""成绩表"两处误写成了 H1（`#`）标题。它们其实是同一个多对多/三表关联案例的组成部分，而不是与"多对多的关系"平级的章节。本笔记已将其规范化为下述子节，**内容与技术细节未作任何改动**。

> [!warning] 源文缺口：省略的成员与访问器
> 上面两处 `//....` / `//...` 是源文的省略占位，`stuId`、`stuNo`、`stuName` 等的 getter/setter 以及 `Subject` 的访问器源文都没有展开。可参考 [[1.MyBatis 环境搭建与快速入门]] 中实体类的写法自行补齐。

#### 接口

```java
package com.neuedu.mapper;
import com.neuedu.entity.more2more.StuInfo;
import java.util.List;
public interface StuInfoMapper {
    List<StuInfo> getStuInfosAndSubjects();//获得所有学生，并且获得每一个学生所有考试科目
}
```

#### 映射文件

```xml
<!-- StuInfoMapper.xml -->

<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.neuedu.mapper.StuInfoMapper">

    <resultMap id="stuInfoBase" type="StuInfo">
        <id column="stu_id" property="stuId"/>
        <result column="stu_no" property="stuNo"/>
        <result column="stu_name" property="stuName"/>
    </resultMap>

    <resultMap id="stuInfoAndSubjectsAdv" type="StuInfo" extends="stuInfoBase">
       <collection property="subjects" column="stu_id" fetchType="lazy" ofType="Subject"
                   select="com.neuedu.mapper.SubjectMapper.getSubjectsByStuInfoId"/>
    </resultMap>
    <select id="getStuInfosAndSubjects" resultMap="stuInfoAndSubjectsAdv">
        select * from t_stu_info
    </select>
</mapper>

<!-- SubjectMapper.xml -->
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.neuedu.mapper.SubjectMapper">

    <select id="getSubjectsByStuInfoId" resultType="Subject" parameterType="int">
        select su.subject_id,su.subject_name,su.subject_cent
        from t_subject su INNER JOIN t_score s on s.score_subject_id=su.subject_id
        where s.score_stu_id=#{id}
    </select>

</mapper>
```

> [!tip] 逐个参数读懂这个 `collection`
> - `property="subjects"` —— 要装配的是 `StuInfo` 里那个叫 `subjects` 的集合属性；
> - **`ofType="Subject"` —— 集合里装的元素类型**（不是 `javaType`，`javaType` 描述的是集合本身的类型）；
> - `column="stu_id"` —— 把主查询结果里的 `stu_id` 列作为参数传给子查询；
> - `select="..."` —— 定位到 `SubjectMapper` 里那条子查询的完整 id；
> - `fetchType="lazy"` —— 延迟加载，只有真正遍历 `subjects` 时才发出这条子查询。
>
> `extends="stuInfoBase"` 让高级 resultMap 复用基础映射，不必把三个字段再写一遍。`resultMap` 与接口代理的基础见 [[2.结果映射与 Mapper 接口]]。

#### 测试

```java
@Test
    public void test009() throws IOException {
        //多对多的关系
        //获得所有学生，并且获得每一个学生所有考试科目
        StuInfoMapper mapper = session.getMapper(StuInfoMapper.class);
        List<StuInfo> stuInfos = mapper.getStuInfosAndSubjects();
        for (StuInfo stuInfo : stuInfos) {
            System.out.println(stuInfo);
            List<Subject> subjects = stuInfo.getSubjects();
            for (Subject subject : subjects) {
                System.out.println(subject);
            }
            System.out.println("=====================================");
        }

    }
```

> [!warning] 这就是 N+1 的雏形
> 先查一次 `t_stu_info`，再对**每个**学生各发一条子查询 —— 3 个学生就是 1+3 条 SQL。学生越多，SQL 越多。这一章先接受它，解决办法（写表连接、一条 SQL 装配到底）见 [[7.关联查询的N+1问题]]。

### 方向三：三表关联——学生 → 成绩 → 科目

**如何知道学生的考试成绩呢？**

**三张表关联的案例**：

1. 新建成绩类，在学生类中，加入一个成绩的集合。
2. 在成绩类中，加入科目的对象，**实现三者之间的关联**。

于是装配路径变成三层：`StuInfo`（一层）→ `List<Score>`（一层，用 `collection`）→ `Score.subject`（一层，用 `association`）。

> [!tip] 三层是怎么一层层装起来的
> 1. `getStuInfosAndSubjectsAndScore` 先执行主查询 `select * from t_stu_info`，每行封成一个 `StuInfo`；
> 2. `stuInfoAndSubjectsAndScoreAdv` 里的 `collection property="scores"` 接住 `stu_id`，调用 `ScoreMapper.getScoresAndSubjectByStuId`，把该学生的每一行成绩封成 `Score`，装进 `List<Score>`；
> 3. 每个 `Score` 上还有 `association property="subject"`，它接住 `score_subject_id`，调用 `SubjectMapper.getSubjectById`，把课程对象挂到 `score.subject` 上。
>
> 于是 `score.getSubject().getSubjectName()` 才取得出课程名 —— 这正是测试代码最后一行打印的东西。
>
> 关键区别只有一处：**`collection` 用 `ofType` 说明集合元素的类型，`association` 用 `javaType`/`property` 说明单个对象的类型。**

public class Tempter {//临时类，用于提供参数，可写可不写
    private int id1;
    private int id2;
    public int getId1() {
        return id1;

    public void setId1(int id1) {
        this.id1 = id1;

    <resultMap id="stuInfoAndSubjectsAdv2" type="StuInfo" extends="stuInfoBase">

> [!tip] 多参数的语法只有两个重点
> - **重点 1（绑定端）**：`column` 由"一个列名"改成 `{key=列名, key=列名}` 的 Map 形式，`key` 是**子查询里 `#{}` 用的名字**，等号右边是**主查询结果里的列名**。
> - **重点 2（接收端）**：子查询的 `parameterType` 写成 `map`，因为 MyBatis 会把 `{key=value}` 装进一个 Map，再用 `#{key}` 取值。
>
> 看 `parameterType="map"` 这一处就明白：**关联查询传多个参数，本质就是把参数塞进一个 Map。**

> [!warning] 源文里几个容易照抄出错的地方
> - `moreParameter` 的 `where` 用的是 `subject_id=#{id1} or subject_id=#{subject_id}`，而 `column` 绑定的是 `{id1=stu_id,subject_id=stu_id}` —— 两个 key 都取自 `stu_id` 列。key 名与列名的对应关系一旦写反，传进去的就不是你期望的值。
> - `resultMap` 的 `column` **只作用于它自己那个子查询**；主查询 `getStuInfosAndSubjectsMoreParameter` 的条件 `where stu_Id=#{id1} or stu_Id=#{id2}` 取的是 `Tempter` 里的 `id1`、`id2`，两者不是同一套参数。
> - 源文最后一句提示：`//查看控制台，打印出的sql，是否提供了多个参数，不关系最终的查询结果` —— 这一步只验证"参数有没有正确传下去"，不必纠结查出来的结果对不对。SQL 日志的开启见 [[3.全局配置与日志]]。

## 易错点

> [!warning] `ofType` 与 `javaType` 别写混
> 集合属性用 `ofType` 指定**元素**类型（`ofType="Subject"`、`ofType="Score"`）；单个对象属性用 `javaType`。给 `collection` 写 `javaType="Subject"` 是错的。

> [!warning] `collection` 的 `column` 必须是主查询结果里真实存在的列
> 三个 `collection` 全部绑定 `stu_id`（或反向的 `subject_id`），因为主查询是 `select * from t_stu_info`，结果里确实有这一列。若主查询只 `select` 了部分字段，`column` 指向的列不存在，子查询就取不到参数。

> [!warning] 子查询的 `select` 要写全限定 id
> 形如 `com.neuedu.mapper.SubjectMapper.getSubjectsByStuInfoId`，是"`namespace` + 标签 `id`"。少写一段就会报找不到语句。

其他常见问题：

| 现象 | 原因 |
|---|---|
| 集合属性是 null | `resultMap` 里漏了 `collection`，或 `collection` 的 `property` 名与实体类字段名不一致 |
| 子查询参数为 null | `column` 的列名在主查询结果里不存在 |
| 子查询报找不到 | `select` 属性没写全限定 id（`namespace` + `id`） |
| 课程名字段取不到 | `Score.toString()` 只打印自己的四个字段，课程名必须 `score.getSubject().getSubjectName()` |
| 明明改了 SQL 但结果没变 | 改了 `StuInfoMapper.xml` 却忘了改 `SubjectMapper.xml`（或反之），两个映射文件是成对出现的 |
| 查询慢、日志刷屏 | 多层 `collection` 延迟加载被逐条触发，即 N+1，见 [[7.关联查询的N+1问题]] |
