# 关联查询、一对一与一对多

前面的单表增删改查，本质是"**一张表 ↔ 一个对象**"：查出来的每一行，正好能填满一个实体类的字段。但真实业务里对象是互相牵连的——员工有身份证，身份证能办多张银行卡。这时候一行记录填不满一个对象，对象里还套着另一个对象或一个集合。

MyBatis 的解法是 **`resultMap` 中的两个标签**：

- `association` —— 处理"一"的方向，把**一个关联对象**装配进某个属性；
- `collection` —— 处理"多"的方向，把**一个集合**装配进某个属性。

## 实体关系如何转换为表

源文先把关系数据库里的实体关系数清楚：

> 数据库中：实体与实体之间的关系（3 种关系，4 种关系（多对一，反向的一对多））

也就是说，**一对多与多对一其实是同一种关系从两端看过去的结果**，所以"3 种"和"4 种"两种说法都能成立。

### 一对一

> 举例：一对一：一个人只有一个身份证信息，一个学生对应一张校园卡，一个工人对应一个工牌信息....

在数据库中，我们可以在任意一张表中，引用另外一张表的主键。

**转换为表的时候，由于只有两个实体，所以是两张表。**

![一对一：两张表通过引用主键关联](mybatis-one-to-one-tables.png)

源文给出的建表代码：

```sql
create table t_emp(
	emp_id int PRIMARY key auto_increment COMMENT '序号',
	emp_no varchar(10) COMMENT '员工号',
	emp_name varchar(10) COMMENT '姓名',
	emp_work_id int COMMENT '职位号',
  emp_card_id int COMMENT '身份证序号',
	FOREIGN key(emp_card_id) REFERENCES t_cardinfo(card_id)
)ENGINE=INNODB default charset=utf8  COMMENT '员工表';



create table t_cardinfo(
	card_id int PRIMARY key auto_increment COMMENT '序号',
	card_no char(18) COMMENT '身份证号',
	card_address varchar(18) COMMENT '户籍所在地'
)ENGINE=INNODB default charset=utf8;
```

> 创建一个实体类，后面需要创建实体类的接口文件 \*Mapper.java 和 实体类的映射文件 \*Mapper.xml

> [!info] 一个实体一套三件套
> 每多一个参与关联的实体，就要多一套 `实体类 + *Mapper.java 接口 + *Mapper.xml 映射文件`。关联查询的代码量之所以显得大，是因为文件的**数量**上去了，而不是单个文件变复杂了。

### 一对多

> 一对多：一个身份证可以办多张银行卡，一个身份证可以办多张手机卡，一个班级中有多个学生

源文特意补了一句**隐含条件**，这句话是判断一对多的关键：

> （隐含条件）一张银行卡属于一个身份证，一个学生只能属于某一个班级（一个学生既属于 1 班，又属于 2 班，错误的）

**转换为表的时候，由于只有两个实体，所以是两张表。**

### 多对多

> 多对多：学生与试卷（课程），读者与图书，学生与老师的关系 .....
>
> 一个学生可以选修多门课程，同一门课程多个学生选修，（两个说法都是成立的）
>
> 一个读者可以借阅多本图书，同一本书在不同的时间可以被多个读者所借阅，（成立）

> 多对多会产生一张关系表，包含两个实体的主键（E-R 转换为表的一个规则）

![多对多：关系表包含两个实体的主键](mybatis-many-to-many-tables.png)

区分口诀：**一端看过去对方是"多"，另一端看过去对方也是"多"，就是多对多**。一对一则是两端看过去都是"一"。

### 数据库设计步骤与转换口诀

源文给出的设计流程：

> 数据库的设计：（1）搜集信息
>
> （2）标识实体
>
> （3）标识属性
>
> （4）标识关系
>
> 生成 E-R 图，-----》 转换为数据库中的表

![数据库设计步骤](mybatis-database-design-steps.png)

四个转换口诀：

| 口诀 | 含义 |
|---|---|
| （1）一个实体对应一张表 | 实体是建表的单位 |
| （2）一个属性对应一个列 | 属性即字段 |
| （3）如果两边实体是一对多的关系，多表中出现一表中的主键 | 外键加在"多"的一方 |
| （4）如果两边实体是多对多的关系，再次新建一张关系表，包含两端的主键 | 关系表只存两个外键 |

> [!tip] 外键加在哪一边
> 口诀（3）是初学者最容易加反的地方：**外键字段出现在"多"的那张表里**。身份证只有一张、银行卡有多张，所以 `t_bank_card` 里存 `card_id`，而不是反过来在 `t_card` 里存一串银行卡号。

## 一对一关系

源文的案例是身份证 `t_card` 与员工 `t_worker`。

### 建表与数据

```sql
create table t_card(
	card_id int PRIMARY KEY auto_increment COMMENT '序号',
	card_no char(18) not null UNIQUE COMMENT '身份证号',
	card_address varchar(50) COMMENT '出生地'
)ENGINE=INNODB DEFAULT charset=utf8 COMMENT '身份证信息表';
select * from t_card;
insert into t_card values(null,'111111111111111111','江苏南京');
insert into t_card values(null,'111111111111111112','江苏徐州');

create table t_worker(
	worker_id int PRIMARY KEY auto_increment COMMENT '序号',
	worker_no char(18) not null UNIQUE COMMENT '工号',
	worker_name varchar(50) COMMENT '姓名',
  worker_card_id int UNIQUE COMMENT '身份证的Id',
	FOREIGN key(worker_card_id) REFERENCES t_card(card_id)
)ENGINE=INNODB DEFAULT charset=utf8 COMMENT '员工信息表';
select * from t_worker;
insert into t_worker values(null,'worker001','张三',1);
insert into t_worker values(null,'worker002','李四',2);
```

注意 `worker_card_id int UNIQUE` —— 这个 `UNIQUE` 就是"一对一"的数据库层面保证：一个员工不能重复引用同一张身份证。

### 映射文件：association + 嵌套查询

```xml
<!-- 编写xml,CardMapper.xml -->
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.neuedu.mapper.CardMapper">

    <!-- 基本的映射关系 -->
    <resultMap id="cardBase" type="Card">
        <id property="cardId" column="card_id"/>
        <result property="cardNo" column="card_no" />
        <result property="cardAddress" column="card_address" />
    </resultMap>
    <!-- extends="" 继承，继承自已有的resultMap，对于基本的字段的映射只要写一次，在这里只写关系映射 -->
    <resultMap id="cardAndWorkerAdv" type="Card" extends="cardBase">
        <!-- association 一对多或一对一，一的方向的处理
         property="worker" 要填充的对象的属性名
         column="" 提供数据的数据库字段
         select="" 要调用的其他xml文件中的id，命名空间+id
         fetchType="eager" 迫切加载（当获得一个身份证信息时，直接查找对应员工信息，不管用户以后是不是使用员工信息）
         fetchType="lazy"  懒加载，延迟加载（当获得一个身份证信息时，不直接查找对应员工信息，当用户使用员工信息时再去查询）
         -->
        <association property="worker" column="card_id" fetchType="eager"
        select="com.neuedu.mapper.WorkerMapper.getWorkerByCardId"/>
    </resultMap>
    <select id="getCards" resultType="Card">
        select * from t_card
    </select>

    <!-- 不能简单的返回一个普通的类，要返回一个自定义resultMap -->
    <select id="getCardsAndWorker" resultMap="cardAndWorkerAdv">
        select * from t_card
    </select>

    <select id="getCardById" resultType="Card" parameterType="int">
        select * from t_card where card_id=#{id}
    </select>
</mapper>

<!--，WorkerMapper.xml-->  
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.neuedu.mapper.WorkerMapper">
    <!-- 基本映射配置 -->
    <resultMap id="workerBase" type="Worker">
        <id property="workerId" column="worker_id"/>
        <result property="workerNo" column="worker_no" />
        <result property="workerName" column="worker_name" />
        <result property="workerCardId" column="worker_card_id" />
    </resultMap>
    <!-- 获得员工以及身份证号 -->
    <resultMap id="workerAndCardAdv" type="Worker" extends="workerBase">
        <association property="card" column="worker_card_id" fetchType="eager"
        select="com.neuedu.mapper.CardMapper.getCardById" />
    </resultMap>

    <select id="getWorkers" resultType="Worker">
        select * from t_worker
    </select>

    <select id="getWorkersAndCard" resultMap="workerAndCardAdv">
        select * from t_worker
    </select>

    <select id="getWorkerByCardId" parameterType="int" resultType="Worker">
        select * from t_worker where worker_card_id=#{id}
    </select>

</mapper>
    
```

这段映射里有几个必须看懂的配合关系：

- `cardAndWorkerAdv` 用 `extends="cardBase"` **继承**了基本字段映射，所以只需要写关系部分；
- `association` 的 `property="worker"` 对应 `Card` 类里新加的 `Worker worker` 属性；
- `column="card_id"` 把当前行的 `card_id` **作为参数传给下一条 SQL**；
- `select="...WorkerMapper.getWorkerByCardId"` 指向的是**另一个 xml 里的语句**，所以要写全 `命名空间 + id`；
- 被调用的 `getWorkerByCardId` 用 `#{id}` 接收这个 `card_id`。

> [!warning] 用了 `association`/`collection` 就不能再写 `resultType`
> 源文在 `getCardsAndWorker` 上方专门标注：**不能简单的返回一个普通的类，要返回一个自定义 resultMap**。凡是需要装配关联对象或集合的查询，`<select>` 必须用 `resultMap="..."`；写 `resultType` 只会装配本表的普通字段，关联属性永远是 `null`。

## 一对多关系

案例换成身份证 `t_card2` 与银行卡 `t_bank_card`：一张身份证对应多张银行卡。

### 一的一方：建立一个集合

> （1）在"一"的一方，建立一个"多"的**集合**

```java
public class Card2 {
    private int cardId;
    private String cardNo;
    private String cardAddress;
    //（1）建立一个集合，保存某一张身份证对饮的所有的银行卡信息
    private List<BankCard> bankCards;

    public List<BankCard> getBankCards() {
        return bankCards;
    }
    //......
}
```

> [!warning] 源文缺口
> `Card2` 中的 `//......` 是源文省略标记，`cardId` / `cardNo` / `cardAddress` 的 getter 与 setter 未展开列出，写法与一对一中的 `Card` 完全一致。另外源文注释里的"对饮"应为"对应"，属源文笔误。

**这是 `association` 与 `collection` 的分水岭**：一对一装的是单个对象，一对多在"一"的一方装的是 `List<...>` 集合。

### 接口

```java
//(1)Card2Mapper
public interface Card2Mapper {
    List<Card2> getCard2AndBankCards();//获得身份证号对应的所有的银行卡

}

//(2)BandCardMapper
public interface BankCardMapper {

}
```

> [!warning] 源文缺口
> 源文此处注释的 `//(2)BandCardMapper` 拼写有误（少一个 `k`），实际接口名以接口声明 `BankCardMapper` 为准；且这个接口在源文此时是**空的**，其方法在后面"多的一方"部分才补上。源文对 `t_card2` 与 `t_bank_card` 的**建表 SQL 未给出**。

### 映射文件：collection + 嵌套查询

```xml
<!-- Card2Mapper.xml -->
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.neuedu.mapper.Card2Mapper">

    <!-- 基本的映射关系 -->
    <resultMap id="card2Base" type="Card2">
        <id property="cardId" column="card_id"/>
        <result property="cardNo" column="card_no" />
        <result property="cardAddress" column="card_address" />
    </resultMap>

    <resultMap id="card2AndBankCardsAdv" type="Card2" extends="card2Base">
        <!--
        property="bankCards" 实体类中的属性
        ofType="BankCard" 集合中元素的类型

<!-- BankCardMapper.xml -->

        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">

    <select id="getBankCardsByCard2Id" resultType="BankCard" parameterType="int">
```

### 多的一方：如何拿到"一"的对方

> 对于"多"的一方，如何获得"一"的一方对象，（参考一对一）
>
> 一个银行卡只能对应一个身份证号

（1）在"多的一方"（银行卡）创建一个"一"的一方（身份证）的**一个对象属性**：

```java
public class BankCard {
    private int bankId;
    private String bankNo;
    private int bankBalance;
    private int bankCardId;
   
    private Card2 card2;//“一”的一方（身份证）的**一个对象属性**
    public Card2 getCard2() {
        return card2;
    }
    public void setCard2(Card2 card2) {
        this.card2 = card2;
    }
    //.....
}
```

**在"多"的一方，装配"一"的对方用的是 `association`，不是 `collection`** ——因为从银行卡看过去，身份证只有一个。方向决定标签，而不是由整个关系叫"一对多"还是"多对一"决定。

（2）编写 xml：

```xml

    <!-- 基本的映射关系 -->

        <id property="cardId" column="card_id"/>
        <result property="cardNo" column="card_no" />
        <result property="cardAddress" column="card_address" />
    </resultMap>

    <resultMap id="card2AndBankCardsAdv" type="Card2" extends="card2Base">
        <!--
        property="bankCards" 实体类中的属性
        ofType="BankCard" 集合中元素的类型
        column="card_id" 提供参数的列
        fetchType="lazy" 延迟加载，默认（不写），一般情况下用于集合的加载
        -->
        <collection property="bankCards" ofType="BankCard" column="card_id" fetchType="lazy"
                    select="com.neuedu.mapper.BankCardMapper.getBankCardsByCard2Id"/>

        select * from t_card2
```

> 两者的区别在于发出 sql 语句的时间
>
> 迫切加载，所有可能用到的数据，全部查询出来，不管后面用户使不使用
>
> 延迟加载，先查出需要的数据，对于集合属性，用到的时候再去查询

日志里能直接读出这个差别：

- **迫切加载**：主查询 `select * from t_worker` 之后，关联 SQL `CardMapper.getCardById` 在**同一个批次里连续发出**，还没轮到打印 `Worker` 对象，数据就已经查完；
- **延迟加载**：主查询 `select * from t_card2` 先完成并打印出 `Card`，等到 `card2.getBankCards()` 被调用时，才**逐条**发出 `BankCardMapper.getBankCardsByCard2Id`。

> [!tip] 什么时候选哪个
> 源文的做法是：一对一（`association`）配 `fetchType="eager"`，一对多（`collection`）配 `fetchType="lazy"`。理由藏在源文的注释里——**"一般情况下用于集合的加载"**：集合展开的 SQL 条数等于主表行数，一次性全查代价太大；而一对一每条主记录只多查一次，代价可控。
>
> 另外源文注明 `fetchType="lazy" 延迟加载，默认（不写）`，即**延迟加载是默认行为**。

> [!warning] 嵌套查询的天生代价：N+1
> 从日志能数出：查 3 张身份证，一共发了 **1 次主查询 + 3 次关联查询**（身份证 3 条，其中一条没有银行卡也照样查了一次）。这就是 N+1 问题，详见 [[7.关联查询的N+1问题]]。

## association 与 collection 对照

| 维度 | `association` | `collection` |
|---|---|---|
| 处理方向 | "一"的方向（一对一） | "多"的方向（一对多） |
| 填充的属性类型 | 单个对象，如 `Worker worker` | 集合，如 `List<BankCard> bankCards` |
| 指定元素类型的属性 | 无（由 `property` 属性的类型决定） | `ofType="BankCard"` |
| 源文注释原话 | "一对多或一对一，一的方向的处理" | "ofType=\"BankCard\" 集合中元素的类型" |
| 源文推荐加载策略 | `fetchType="eager"` | `fetchType="lazy"` |

`javaType` 与 `ofType` 的区别，可以用一句话记住：**`javaType` 描述"这个属性本身是什么类型"，`ofType` 描述"集合里面装的是什么类型"**。一对多时属性本身是 `List`，元素是 `BankCard`，所以用 `ofType` 告诉 MyBatis 该把每一行映射成哪个类。

> [!warning] 源文缺口
> 本篇章（第 827-1458 行）中**只出现了 `ofType`，没有出现 `javaType`**；上面对 `javaType` 的概括属于通用语义说明，源文在本章未给出 `javaType` 的用例。另外，本章的关联查询**全部走"嵌套查询（`select` 指向另一条语句）"这一条路线**，源文没有在本章演示"嵌套结果（一条 join SQL 用 `resultMap` 直接映射）"的写法。

> [!info] 两条路线：嵌套查询 vs 嵌套结果
> - **嵌套查询**（本章用法）：`<association select="...">`，主查询正常查主表，MyBatis 再按 `column` 逐行调用另一条语句。特点是 SQL 好写、可复用，但会产生 N+1 次查询。
> - **嵌套结果**：只发一条带 `join` 的 SQL，在 `resultMap` 里直接描述"哪些列映射到主对象、哪些列映射到关联对象"。只有一次查询，但需要处理多行合并，且 XML 更繁琐。
>
> 本章内容全部属于前者。

## 易错点

> [!warning] 关系方向决定用哪个标签，而非关系名称
> 同为"一对多关系"，在"一"的一方（`Card2`）用 `collection`，在"多"的一方（`BankCard`）仍用 `association`。判断标准只有一个：**当前实体里那个属性的类型是单个对象还是集合**。

> [!warning] `select` 必须写全 `命名空间 + id`
> `<association select="com.neuedu.mapper.WorkerMapper.getWorkerByCardId"/>`。只写 `getWorkerByCardId` 无法跨 xml 定位。同时该 id 在目标 xml 中必须真实存在。

> [!warning] 一对多忘了 `ofType`
> `collection` 只写 `property` 不写 `ofType`，MyBatis 不知道该把结果行映射成哪个类，会报错或映射失败。`ofType` 是 `collection` 的必填项。

> [!warning] 关联查询用 `resultType` 会"静默变 null"
> 见上文的 `<!-- 不能简单的返回一个普通的类，要返回一个自定义resultMap -->`。用了 `resultType` 程序不报错，但关联属性是 `null`，最容易误判为"数据没查到"。

其他常见问题：

| 现象 | 原因 |
|---|---|
| 关联属性为 `null` | `<select>` 用了 `resultType` 而非 `resultMap` |
| 报"找不到语句" | `select` 属性没写全 `命名空间 + id`，或目标 xml 未注册进 `mybatis-config.xml` 的 `<mappers>` |
| 关联对象查不到或查错 | `column` 指定的列不是外键列 |
| 集合元素类型错误 | `collection` 缺 `ofType` 或 `ofType` 写错类名 |
| 基本字段映射重复写 | 未用 `extends="xxxBase"` 继承基础 `resultMap` |
| 一次性发出大量 SQL | 嵌套查询固有的 N+1，见 [[7.关联查询的N+1问题]] |
| 集合属性访问时才发 SQL | 这是 `fetchType="lazy"` 的默认行为，不是 bug |
| 一对一/多对一混淆 | 外键加错了表，口诀见"四个转换口诀" |
