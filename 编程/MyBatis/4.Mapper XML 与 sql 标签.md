> 完全限定名：包名.类名

即在需要写全类型的地方，写法是"包名 + 点 + 类名"，例如 `com.neuedu.entity.Stu`。

## sql 标签

`<sql>` 片段的作用，源文一句话概括（第 632 行）：

> 编写 sql 语句时更加的统一，更方便修改

### 为什么需要统一维护：`select *` 的代价

源文（第 634-645 行）给出一段推理，核心是三种代价之间的权衡：

- 在 SQL 查询中，**使用 `*` 是最慢的**。
- 源文对慢的原因给的解释是：**SQL 语句是从后向前扫描、解析的**。
  - 先获得表名。
  - 如果遇到 `*`，就要**解析整张表以获得全部的列**——源文称这是"最慢、最耗时的"。
  - 而写成 `select stu.stu_id, stu.stu_name, stu.stu_no from t_stu_info stu` 时，解析过程已经知道有一个表（`t_stu_info`）别名是 `stu`；遇到 `stu.stu_id` 这类写法就**直接使用，不必遍历表的结构**。
- 但 `select *` 并非全无好处：它**编写起来比显式列名要快**，而且**当表的结构发生变化时，`select *` 不用任何修改**。
- 显式列名的代价在于：表新增列后，语句需要修改；**如果在 xml 中多次出现这个语句，修改量很大**。

把这段推理整理成一个代价对比表（结论均来自源文，未添加任何性能数字或基准测试）：

| 写法 | 编写便利 | 解析开销 | 表结构变更后的维护量 |
|---|---|---|---|
| `select * from t_stu_info` | 高：不必逐列列出 | 高：遇到 `*` 需解析整表以取得全部列，源文称"最慢、最耗时" | 低：新增列后语句无需修改 |
| 显式列名（如 `stu.stu_id, stu.stu_name, stu.stu_no`） | 低：需要逐列书写 | 低：已知表与别名，遇到 `stu.stu_id` 直接使用，不必遍历表结构 | 高：新增列要改；同一语句在 xml 中多处出现时，修改量很大 |

两种写法各自赢一半：**性能**要求显式列名，**便利与抗变更**要求 `select *`。`<sql>` 片段正是用来把显式列名集中到一处——既拿到显式列名的解析效率，又把"多处修改"收敛成"一处修改"。

### 用法三步

#### （1）修改 xml 文件，加入并引用 sql 标签

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.neuedu.mapper.StuMapper">
    <!--
    ${要传入的参数}.stu_id列名
    ${要传入的参数} 给表起别名时，使用的是不同的别名
    -->
    <sql id="sqlBase001">
        ${alias}.stu_id as stu_id , ${alias}.stu_name,${alias}.stu_no
    </sql>
    <sql id="sqlBase002">
        stu_id as stu_id , stu_name , stu_no
    </sql>
    <!-- 实现属性与数据库中字段的手动映射
    <resultMap>
    id="名字的唯一" type="对应的实体类的类型"
    <id> 用于主键列的处理
    <result>用于普通列的处理
    property="java类的属性" column="数据库中的字段"
     -->
    <resultMap id="stuBase" type="Stu">
        <id property="stuId" column="stu_id"/>
        <result property="stuNo" column="stu_no" />
        <result property="name" column="stu_name" />
    </resultMap>


    <select id="selectAll" resultType="Stu">
        select * from t_stu_info
    </select>
    <!-- resultMap 使用自己编写的映射标签，引用自己编写的resultMap标签的 id  -->
    <select id="selectAll2" resultMap="stuBase">
        select * from t_stu_info
    </select>
    <select id="selectStuById" parameterType="int" resultMap="stuBase">
        select * from t_stu_info where stu_id=#{id}
    </select>
    <!-- 调用sql标签 -->
    <select id="selectAll_1" resultType="Stu">
        select
        <include refid="sqlBase001">
            <property name="alias" value="t1"/>
        </include>
        from t_stu_info t1
    </select>
    <!-- resultMap 使用自己编写的映射标签，引用自己编写的resultMap标签的 id  -->
    <select id="selectAll2_1" resultMap="stuBase">
        select
        <include refid="sqlBase001">
            <property name="alias" value="t2"/>
        </include>
        from t_stu_info t2
    </select>
    <select id="selectStuById_1" parameterType="int" resultMap="stuBase">
        select
        <include refid="sqlBase001">
            <property name="alias" value="t3"/>
        </include>
        from t_stu_info t3 where t3.stu_id=#{id}
    </select>
</mapper>
```

结构要点：

- `<sql id="...">` 定义片段，`id` 是片段名。
- `<include refid="...">` 在需要的地方引用片段，`refid` 对应 `<sql>` 的 `id`。
- 片段内部用 `${alias}` 作为**别名占位符**；引用时通过子标签 `<property name="alias" value="t1"/>` 传入具体的别名。源文注释说明这样做的原因是"给表起别名时，使用的是不同的别名"，因此三个查询分别传入了 `t1`、`t2`、`t3`。

> [!warning] `${}` 与 `#{}` 在这里的分工
> 片段里的 `${alias}` 不是预编译占位符，而是**字符串拼接**：`<include>` 传入什么，就原样拼进 SQL。所以它只能用来替换**表别名这类 SQL 结构**，值必须由 `<property>` 在 XML 内给定，**不能让外部输入流到这里**。参数值的绑定仍要用 `#{}`（如 `where t3.stu_id=#{id}`）。源文只写了占位符的用途，未展开这层区别。
>
> 需注意与源文第 234-236 行一致：`parameterType="int"` 时系统自动提供 `#{id}`。

> [!warning] 别名必须与 `FROM` 中实际写的别名一致
> 本节的 `<include>` 传 `t1`，`from` 子句就写 `from t_stu_info t1`；`selectStuById_1` 传 `t3`，`where` 也必须写 `t3.stu_id`。二者不一致时，生成的 SQL 会引用一个不存在的别名。

> [!info] 源文中定义而未使用的片段
> 上面的 `<sql id="sqlBase002">`（`stu_id as stu_id , stu_name , stu_no`，不带别名占位符）在这一节的 XML 里**被定义但没有任何 `<select>` 引用它**。可以把它理解为"无需别名的版本"，源文未给出它的用例。

> [!tip] 片段与 `resultMap` 的搭配
> `sqlBase001` 输出的列名是 `stu_id`、`stu_name`、`stu_no`。源文第 382-433 行说明过：`Stu` 的属性 `name` 与列名 `stu_name` 不遵循驼峰映射，只写 `resultType` 时 `name` 取不到值。因此示例中带别名的两个查询（`selectAll2_1`、`selectStuById_1`）用的是 `resultMap="stuBase"`；而 `selectAll_1` 用的是 `resultType="Stu"`，按源文同一处的道理，`name` 同样不会被填充。映射原理见 [[2.结果映射与 Mapper 接口]]。

#### （2）修改接口代码

```java
public interface StuMapper {
    List<Stu> selectAll();//获得全部
    List<Stu> selectAll2();//获得全部
    Stu selectStuById(int id);//通过主键查询

    // 使用sql标签的
    List<Stu> selectAll_1();//获得全部
    List<Stu> selectAll2_1();//获得全部
    Stu selectStuById_1(int id);//通过主键查询
}
```

接口方法名与 XML 标签的 `id` 一一对应，靠 `session.getMapper(StuMapper.class)` 的代理完成调用。

## 加入 JUnit

用 `main` 方法测试的缺点是：一个类只能有一个入口，想测多个方法就要反复改代码。JUnit 用注解描述"测试前做什么、测试后做什么、哪些方法是测试用例"，于是同一个类里可以并排放多个独立测试。

### （1）下载依赖，修改 pom.xml

```xml
<!-- https://mvnrepository.com/artifact/junit/junit -->
<dependency>
    <groupId>junit</groupId>
    <artifactId>junit</artifactId>
    <version>4.12</version>
</dependency>
```

> [!warning] 版本来自源文，不是当前推荐
> `junit 4.12` 是源文写作时使用的版本，**照抄可复现源文环境**，但不要据此认为它是最新版本。依赖可在 [mvnrepository](https://mvnrepository.com/) 查询。

### （2）编写测试代码

```java
package com.neuedu.test;

import com.neuedu.entity.Stu;
import com.neuedu.mapper.StuMapper;
import org.apache.ibatis.io.Resources;
import org.apache.ibatis.session.SqlSession;
import org.apache.ibatis.session.SqlSessionFactory;
import org.apache.ibatis.session.SqlSessionFactoryBuilder;
import org.junit.After;
import org.junit.Before;
import org.junit.Test;

import java.io.IOException;
import java.io.InputStream;

public class JunitTest {

    SqlSession session;
    //测试代码执行前先执行这个函数
    @Before
    public void myBegin() throws IOException{
        //查找根目录
        InputStream is = Resources.getResourceAsStream("mybatis-config.xml");
        SqlSessionFactory factory = new SqlSessionFactoryBuilder().build(is);
        session =factory.openSession();//打开session
    }
    //当测试代码执行完毕后，执行after注解的函数
    @After
    public void myClose(){
        session.close();//用完关闭session
    }

    @Test
    public void test001() {
        StuMapper mapper = session.getMapper(StuMapper.class);//通过代理，获得自定义的接口对象
        Stu stu = mapper.selectStuById_1(1);//对参数的类型进行的判断
        System.out.println(stu);
    }
    @Test
    public void test002() throws IOException {
        StuMapper mapper = session.getMapper(StuMapper.class);//通过代理，获得自定义的接口对象
        Stu stu = mapper.selectStuById(1);//对参数的类型进行的判断
        System.out.println(stu);
    }
}
```

> [!info] 关于上段代码
> 源文类名前还有一段 javadoc（含作者、联系方式、日期、项目名），与代码语义无关，此处略去；其余内容照抄源文第 766-821 行。

三个注解的分工：

| 注解        | 作用                   | 源文对应说明                    |
| --------- | -------------------- | ------------------------- |
| `@Before` | 每个测试方法执行**前**都先执行一次  | "测试代码执行前先执行这个函数"          |
| `@After`  | 每个测试方法执行**完毕**后都执行一次 | "当测试代码执行完毕后，执行after注解的函数" |
| `@Test`   | 标记一个测试用例             | 被标记的方法会被 JUnit 自动执行       |

`session` 被提升为**成员变量**，正是为了让 `@Before` 里打开的 session 能被每个 `@Test` 方法使用、再由 `@After` 统一关闭。

> [!tip] 这正是 `@Before` / `@After` 的价值
> 两段 `@Test` 方法里不再出现任何初始化与关闭代码，重复的三段式骨架只写了一遍。

## 易错点小结

| 现象 | 原因 |
|---|---|
| `select` 出来的 `name` 是 `null` | 属性 `name` 与列名 `stu_name` 不遵循驼峰映射，只写 `resultType` 无法自动填充；应使用 `resultMap`（源文 382-433 行） |
| 引用片段后 SQL 报别名不存在 | `<include>` 传入的 `<property name="alias">` 与 `from` 子句中的别名不一致 |
| 片段定义后不起作用 | `<sql>` 只被定义、没有被 `<include refid="...">` 引用（如本节的 `sqlBase002`） |
| 想改列名要改很多地方 | 语句在 xml 中多处出现且写的是显式列名——这正是 `<sql>` 片段要解决的问题 |
| JUnit 测试报 session 为 null | `@Before` / `@After` 注解缺失或写错包（必须是 `org.junit.Before`、`org.junit.After`） |
