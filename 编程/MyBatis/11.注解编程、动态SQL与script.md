# 注解编程、动态SQL与script

注解里的 SQL 是写死的字符串，一旦需要"按条件拼接"，字符串加法很快就不可读了。源文给出两条出路：

- **`@*Provider`**：把 SQL 生成逻辑从接口里搬出去，放到一个普通的 Java 类中，用 `if` 判断拼出 SQL 字符串；
- **`<script>`**：把 XML 风格的动态标签（`<where>`、`<if>`）塞进注解的字符串里，让 MyBatis 按 XML 动态 SQL 的规则解析。

前者是"用 Java 写 SQL"，后者是"在注解里用 XML 写 SQL"。本篇承接 [[9.注解编程、基础CRUD]] 的注解基础写法，示例中出现的 `@Results` / `@One` 属关系映射，见 [[10.注解编程、关系映射]]。

## 注解中的动态 sql

### 使用 `@*Provider`

星号代表 `Select`、`Insert`、`Update`、`Delete`，即 `@SelectProvider`、`@InsertProvider`、`@UpdateProvider`、`@DeleteProvider`。源文原话是"使用向导处理"，并把承载 SQL 生成逻辑的那个类称作**向导类**（Provider）。

Provider 注解只有两个要素：

| 要素 | 含义 |
|---|---|
| `type` | 确定要调用的类 |
| `method` | 确定类中生成 sql 语句的方法 |

> [!warning] 源文只演示了 `@SelectProvider`
> 源文在此列出的是 `@*Provider` 一整族注解，但**给出的全部代码示例都只用到了 `@SelectProvider`**；`@InsertProvider`、`@UpdateProvider`、`@DeleteProvider` 的用法在源文区间内没有示例，需要时请自行查阅官方文档，不要照着本篇示例推断它们的参数写法。

下面两个小节的区别只在**Provider 方法接收什么参数**：`Map` 还是实体对象。

#### Map 集合作为参数

第一步是新建一个普通的类，方法返回字符串，这个字符串就是通过代码生成出来的 SQL 语句：

```java
//com.neuedu.provider.MyProvider
// 对应的方法返回一个字符串，这个字符串，就是通过代码生成sql语句
public class MyProvider {
    public  String sql001(Map<String,Object> params){
       return new SQL(){
           {
               SELECT("*");
               FROM("t_card");
               if(params.get("id")!=null){
                   WHERE("card_id >= #{id}");
               }
               if(params.get("no")!=null){
                   OR();//默认不写条件之间的关系，就是and，我们手动设置的or的方式
                   WHERE("card_no like #{no}");
               }
           }
       }.toString();
    }
}
```

```java
//接口
public interface CardMapperAnnotation {
    //获得所有的身份证号，同时获得对应的员工信息
    @Select("select * from t_card")
    @Results(id="cardWorkerAdv2",value={
            @Result(property = "cardId",column = "card_id"),
            @Result(property = "cardNo",column = "card_no"),
            @Result(property = "cardAddress",column = "card_address"),
            @Result(property = "worker",column = "card_id",one = @One( fetchType = FetchType.EAGER,
                    select = "com.neuedu.mapper.WorkerMapperAnnotation.getWorkerByCardId")),//注意注解中的写法select = "包名.接口名.方法名" 完全限定名
    })
    List<Card> getCardsAndWorker();

    //通过xml方式去调用
    @Select("select * from t_card")
    @Results(id="cardWorkerAdv3",value={
            @Result(property = "cardId",column = "card_id"),
            @Result(property = "cardNo",column = "card_no"),
            @Result(property = "cardAddress",column = "card_address"),
            @Result(property = "worker",column = "card_id",one = @One( fetchType = FetchType.EAGER,
                    select = "com.neuedu.mapper.WorkerMapper.getWorkerByCardId")),//也可以调用xml文件中的对应的方法
    })
    List<Card> getCardsAndWorker2();

    //注解动态sql
    //type = com.neuedu.provider.MyProvider.class 普通的工具类 ,method = "sql001" 类中对应的方法
    @SelectProvider(type = com.neuedu.provider.MyProvider.class,method = "sql001")
    List<Card> getCardsByProvider(Map ma);

}
```

> [!tip] 这段接口里，动态 SQL 只体现在最后三行
> 前面的 `getCardsAndWorker` / `getCardsAndWorker2` 是关系映射的写法（`@Results` + `@One`），放在这里是源文接口的完整上下文，与本篇主题无关，见 [[10.注解编程、关系映射]]。
>
> 真正要看的只有 `@SelectProvider(type = com.neuedu.provider.MyProvider.class, method = "sql001")` 一行：SQL 从此不由注解里的字符串决定，而由 `MyProvider.sql001` 的返回值决定。

#### 对象作为参数

实体对象同样可以作为 Provider 方法的参数，判断条件时直接调用 getter：

```java
//为什么在写实体类时都用封装类，而不是使用基本数据类型
public class Card {
    //属性是有默认值的，int 不写时，默认是0，0在后期开发过程中，可能是一个有效的值，所以使用0作为默认值就不合适了
    //如果使用封装类，我们就多了一个默认值null
    private int cardId;//如果使用MyBatis，属性一般情况，都使用封装类作为它的数据类型，不会使用基本数据类型
    //...
}
//向导类
public class MyProvider {
    public  String sql001(Map<String,Object> params){
       return new SQL(){
           {
               SELECT("*");
               FROM("t_card");
               if(params.get("id")!=null){
                   WHERE("card_id >= #{id}");
               }
               if(params.get("no")!=null){
                   OR();//默认不写条件之间的关系，就是and，我们手动设置的or的方式
                   WHERE("card_no like #{no}");
               }
           }
       }.toString();
    }

    public  String sql002(Card card){
        return new SQL(){
            {
                SELECT("*");
                FROM("t_card");
                if(card.getCardId()!=0){
                    WHERE("card_id >= #{cardId}");//#{id}对应的key就是属性名称
                }
                if(card.getCardNo()!=null){
                    OR();//默认不写条件之间的关系，就是and，我们手动设置的or的方式
                    WHERE("card_no like #{cardNo}");
                }
            }
        }.toString();
    }
}
```

```java
//接口

    List<Card> getCardsByProvider2(Card card);
//测试
@Test

        CardMapperAnnotation mapper = session.getMapper(CardMapperAnnotation.class);
        Card card1 = new Card();
        card1.setCardId(10);
        card1.setCardNo("%111%");
        List<Card> cards = mapper.getCardsByProvider2(card1);
        for (Card card : cards) {
            System.out.println(card);
        }
    }
```

```text
[com.neuedu.mapper.CardMapperAnnotation.getCardsByProvider2]-==> Parameters: 10(Integer), %111%(String)
[com.neuedu.mapper.CardMapperAnnotation.getCardsByProvider2]-<==      Total: 2

Card{cardId=2, cardNo='111111111111111112', cardAddress='江苏徐州'}   
```

> [!info] 为什么实体类属性一律用封装类型
> 源文借 `Card` 类解释了这个贯穿全篇的习惯：基本类型有"静默默认值"——`int` 不赋值就是 `0`，而 `0` 在业务里可能是一个合法值（比如 `cardId = 0`），于是"没传值"和"传了 0"就分不出来了。换成 `Integer`，多出一个 `null` 默认值，`if (card.getCardId() != null)` 才能真正表达"这个条件不参与拼接"。
>
> 也正因如此，源文 `sql002` 里写的判断是 `card.getCardId()!=0`——这是**照抄源文、与 `int` 字段配套**的写法。若把 `cardId` 改成 `Integer`，判断应相应改为 `!= null`，否则 `card.getCardId()!=0` 会因自动拆箱对 `null` 抛 `NullPointerException`。

> [!info] `#{cardId}` 里的名字从哪来
> Provider 方法返回的是一段 SQL **字符串**，MyBatis 拿到后仍按普通 SQL 解析占位符：`#{cardId}` 取的是参数对象 `card` 的 `cardId` 属性，所以源文注释写"`#{id}` 对应的 key 就是属性名称"。Map 参数则是 `#{id}` 对应 `map.get("id")`。

> [!warning] 源文缺口：实体类与方法签名不完整
> - `Card` 类在源文中只给出了 `cardId` 字段及注释，其余字段与 getter/setter 用 `//...` 省略；`card.getCardNo()`、`setCardNo()`、`setCardId()` 的方法定义同样未给出。
> - `getCardsByProvider(Map ma)` 使用了 Map 的**原始类型**写法（无泛型），源文如此，此处照抄，不做"优化"。
> - `SQL` 类（`org.apache.ibatis.jdbc.SQL`）、各注解与 JUnit 的 `import` 语句在源文的 Provider 示例中均未给出。

## 使用 `<script>` 直接编写 sql 语句

不新建 Provider 类，直接在注解的字符串里用 `<script>` 包住 XML 风格的动态标签即可：

```java
//接口
    @Select("<script> " +
            "select * from t_card " +
            "<where> " +
            "      <if test=\"cardId != null\"> and card_id = #{cardId} </if>  " +
            "      <if test=\"cardNo != null\"> and card_no like #{cardNo} </if>  " +
            "</where>  " +
            "</script>  ")//字符串中包含动态sql的代码
    List<Card> getCardsByProvider3(Card card);

    @Select("<script> " +
            "select * from t_card " +
            "<where> " +
            "      <if test=\"cardId != null\"> and card_id &lt;= #{cardId} </if>  " +
            "      <if test=\"cardNo != null\"> and card_no like #{cardNo} </if>  " +
            "</where>  " +
            "</script>  ")//字符串中包含动态sql的代码
    List<Card> getCardsByProvider4(Card card);
```

```java
//测试
@Test

```

```text
//结果
[com.neuedu.mapper.CardMapperAnnotation.getCardsByProvider4]-==>  Preparing: select * from t_card WHERE card_id <= ? and card_no like ? 
[com.neuedu.mapper.CardMapperAnnotation.getCardsByProvider4]-==> Parameters: 10(Integer), %111%(String)
[com.neuedu.mapper.CardMapperAnnotation.getCardsByProvider4]-<==      Total: 2
Card{cardId=1, cardNo='111111111111111111', cardAddress='江苏南京'}
Card{cardId=2, cardNo='111111111111111112', cardAddress='江苏徐州'}
```

`getCardsByProvider3` 与 `getCardsByProvider4` 的唯一差别是条件运算符：前者 `=`，后者 `<=`。因为 `<` 是 XML 标记字符，写 `<=` 时必须写成 `&lt;=`，所以 `3` 与 `4` 实际上是"不涉及小于号"和"涉及小于号"两个对照写法。`<where>` 与 `<if>` 的行为与 XML 文件中的动态 SQL 完全一致，见 [[8.动态 SQL]] 与 [[4.Mapper XML 与 sql 标签]]。

### 四条注意事项

源文对该写法给出的注意事项（编号为源文原有编号）：

1. `<script>` 标签不要写错；
2. 双引号需要转义 `\"`；
3. 编写内容时，每一行后面加一个空格，防止出现多个单词粘连成一个单词；
4. 如果遇到使用大于号与小于号时，要使用转义字符，参见 xml 文件的转义字符。

> [!warning] 第 3 条不是格式洁癖，是语法问题
> 字符串拼接（`+`）时容易漏掉行尾空格，`"...t_card "` 少了那个空格就会拼成 `...t_card<where>` 之类的粘连文本，SQL 直接语法错误。所以源文特意在每段字符串尾部都留了空格，`</script>  ` 后面甚至留了两个。

> [!warning] 第 2 条：`test` 属性里的引号必须转义
> `@Select("... <if test=\"cardId != null\"> ...")` 中外层是 Java 字符串的双引号，`test` 属性的值又要用双引号，内层只能用 `\"`。源文示例中每一处 `test` 都是这个写法，不要改成单引号后忘记验证。

### XML 转义字符表

源文以"方法一 使用 xml 转义符"为标题给出了这张对照表：

| 转义符 | 字符 | 含义 |
|---|---|---|
| `&lt;` | `<` | 小于 |
| `&lt;=` | `<=` | 小于等于 |
| `&gt;` | `>` | 大于 |
| `&gt;=` | `>=` | 大于等于 |
| `&amp;` | `&` | 和 |
| `&apos;` | `'` | 单引号 |
| `&quot;` | `"` | 双引号 |

整表记一条规律即可：需要转义的字符都出现在**被 XML 解析器解析的那一层**，`<`、`>`、`&` 是 XML 的标记与实体起始符，引号在属性值里需要转义。

> [!info] 出处与"方法二"
> 该转义表为源文收录的外部资料整理，源文标注为"方法一"，并在末尾另有第三方署名与链接；**"方法二"在源文该区间内并未给出**，属源文缺口。
>
> 另可对照 [[4.Mapper XML 与 sql 标签]] 中提到的 `<![CDATA[ ... ]]>`：CDATA 里内容原样输出，`>`、`<` 无需改写，可以视作不使用转义符的另一条路（源文此处未将其列为同一张表的"方法二"）。

## 易错点

> [!warning] 两种"写错"都会在运行时报 SQL 语法错误，而不是编译错误
> Provider 方法返回的是字符串，`<script>` 里写的也是字符串，Java 编译器对它们一无所知。拼错了只有执行时 MyBatis 解析 / 数据库执行才报错，所以日志里那条 `Preparing: ...` 是排查的第一现场。

| 现象 | 原因 |
|---|---|
| `Preparing:` 里出现单词粘连 | 字符串拼接漏了行尾空格（注意事项 3） |
| `test=\"...\"` 编译不过 | `test` 属性值用了未转义的双引号（注意事项 2） |
| 报 XML 解析错误 / 标签找不到 | `<script>` 标签写错，或动态标签未闭合（注意事项 1） |
| `<=` 处报 XML 或 SQL 错误 | 小于号未写成 `&lt;=`（注意事项 4） |
| Provider 方法返回 `null` 或 SQL 为空 | `method` 名与 Provider 类中的方法名不一致，或 `if` 分支全部未命中 |
| 条件明明传了值却不生效 | Provider 中以 `int` 字段判断 `!= 0`，值为 0 被当成了"未传" |

> [!tip] 该选哪条路
> - 拼接逻辑复杂、希望用 Java 调试：用 `@*Provider`，SQL 生成过程可以在 Provider 方法里打断点；
> - 条件不多、且已经熟悉 XML 动态 SQL 标签：用 `<script>`，改动最小，与 XML 写法可以直接互相搬运。
>
> 无论哪条路，MyBatis 最终拿到的都是一段完整 SQL，因此结果映射、`@Results`、`@One` 等写法完全不受影响。
