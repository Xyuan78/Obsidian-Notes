# 关联查询的N+1问题

关联查询有两种写法：一种是**主查询查出 N 条主记录后，再对每条主记录发一条子查询**；另一种是**一条 SQL 用表连接把主表与关联表的数据一次取回**。前者就是 N+1 问题。本篇按源文的顺序，先看那个**源文自己标注了「有问题的」**写法，再看源文标注为「可以使用的」写法。

## 什么是 N+1 问题

关联查询中，如果嵌套部分用的是「再发一条 select」的思路（嵌套 select）：先查 1 次主表，拿到 N 条主记录，然后为了填充每一条主记录里的关联属性，再发出 N 条子查询。数据库往返次数就是 **1 + N**，「N+1」这个叫法由此而来。

它的代价不在结果的**对不对**，而在**查询的条数**：

- 往返次数随主记录条数线性增长——主表里有多少条记录，就要多发多少条 SQL；
- 每一次嵌套查询都是一次独立的数据库交互，无法被一条 SQL 覆盖。

源文处理这件事的落点很直接：用**表连接**把关联数据一次取回。源文在查询标签的注释里就是这个意思：

> [!info] 源文原话
> 「写表连接防止出现 n+1 的情况，通过写表连接，只发出一条 sql 语句，实现所有关联数据的填充。」

也就是说，源文给出的解法方向是**由「多次查询」改为「一条表连接 SQL」**。下面两个小节分别对应源文里错误与正确的两种落地方式。

## 写法一：源文标注为「有问题的」写法

源文这一节的标题原文即为 `### 处理sql关联查询的n+1问题  (有问题的)`，括号里的「有问题的」是源文自己加的判断。

### 高级 resultMap 的嵌套写法

源文原样如下：

```xml
<resultMap id="readerAndHis3" type="MyReader" extends="readerBase">
        <collection property="his" column="reader_id" ofType="ReadHis" fetchType="lazy">
            <!-- 如果在映射时，属性与列不匹配，也可以处理映射关系
            <id property="fid" column="fid"/>
            <result property="fname" column="fname"/>
			-->
            <association property="book" column="book_id" fetchType="eager"/>
        </collection>
</resultMap>
```

### 查询标签

```xml
    <!-- 写表连接防止出现n+1的情况
    ，通过写表连接，只发出一条sql语句，实现所有关联数据的填充，
    -->
    <select id="getRreaderAndHis3" resultMap="readerAndHis2">
           select b.* ,r.*,h.read_time from book b
   			INNER JOIN read_his h on h.book_id = b.book_id
   			INNER JOIN reader r on r.reader_id=h.reader_id
    </select>
```

> [!warning] 这段为什么是错的
> 请对照上面的源码逐条看，源文**自己**已经埋下了矛盾之处：
> 1. **「用表连接解决 N+1」的注释，配的却是嵌套装配的 resultMap。** 注释说要「只发出一条 sql 语句，实现所有关联数据的填充」，可 `readerAndHis3` 里的 `<collection>` 与 `<association>` **都没有写 `select` 属性**，也就是没有指明要调用的子查询；同时也没有像写法二那样用 `resultMap` 指向另一个映射。既没有 `select` 也没有 `resultMap` 的嵌套节点，无法靠它完成关联数据的填充。
> 2. **`resultMap` 名对不上号。** `resultMap` 定义的 id 是 `readerAndHis3`，而 `<select>` 里写的是 `resultMap="readerAndHis2"`。二者不是同一个 id。
> 3. **`MyReader`、`ReadHis` 的名字出现在 `type` / `ofType` 里，但 `readerBase` 这个被 `extends` 的 resultMap 源文未给出。**
>
> 因此源文标题里那句「有问题的」是有据可依的：这段代码从映射名到嵌套节点都不成立，**不能当作可行方案照抄**。它在本篇里的作用只能是反例——它展示的正是「想把表连接与嵌套装配拼在一起，却两边的要素都没配齐」的中间状态。

这段测试本身没有问题：`MyReader.his` 是借阅历史集合，`ReadHis.book` 是历史记录对应的图书对象，测试做的就是「遍历读者 → 遍历其借阅历史 → 打印每本书的名字与阅读时间」。问题出在**上面那段映射配置**，而不是测试的调用方式。

> 源文只给出了三张表里的两张、`readerBase` 映射以及 `ReadHis` 其余字段（如 `hisId`、`readerId`、`bookId` 的驼峰字段）的完整定义。照抄测试代码前需要自行补全这些部分。

## 写法二：源文标注为「可以使用的」写法

源文这一节的标题为 `### n+1的另外一种处理办法（可以使用的）`。源文以 `t_stuinfo` / `t_score` / `t_course` 三张表为例，完整给出了映射链路。

```xml
学生类映射配置 
 <resultMap id="stuAndScoresAndCourse01" type="StuInfo" extends="stuInfoBase">
        <collection property="scores" column="stu_id" ofType="Score" fetchType="eager"
            resultMap="com.zsp.mapper.ScoreMapper.scoreAndCourse">
        </collection>
</resultMap>
学生的查询语句
<select id="getAllStus" resultMap="stuAndScoresAndCourse01">
        SELECT st.*,co.*,s.*
        from t_stuinfo st left JOIN t_score s on s.sc_stu_id=st.stu_id
                          left JOIN t_course co on s.sc_cou_id=co.cou_id
</select>

成绩的映射配置
 <resultMap id="scoreAndCourse" type="Score" extends="scoreBase">
        <association property="course" fetchType="eager" column="sc_cou_id"
                   resultMap="com.zsp.mapper.CourseMapper.courseBase"/>
</resultMap>

课程的映射配置
    <resultMap id="courseBase" type="Course">
        <result property="couId" column="cou_id"/>
        <result property="couNo" column="cou_no"/>
        <result property="couName" column="cou_name"/>
        <result property="couCent" column="cou_cent"/>
    </resultMap>
```

> [!note] 源文原样保留
> 上面代码块中混在 XML 之间的中文（「学生类映射配置」「学生的查询语句」「成绩的映射配置」「课程的映射配置」）是源文原有的分隔说明，不是注释语法，此处照抄。

### 它为什么可行

三点，全部对应源文代码本身：

1. **查询次数是 1。** `<select id="getAllStus">` 里是一条 `SELECT`，用两次 `LEFT JOIN` 同时取出学生、成绩、课程三张表的列。源文在写法一的注释里所说的「只发出一条 sql 语句，实现所有关联数据的填充」，在这段代码上才真正成立。
2. **嵌套节点用 `resultMap` 指向另一个映射，而不是 `select` 再发一条查询。** `<collection>` 与 `<association>` 上写的是 `resultMap="..."`（分别指向 `com.zsp.mapper.ScoreMapper.scoreAndCourse` 与 `com.zsp.mapper.CourseMapper.courseBase`），而不是 `select="..."`。这意味着关联对象是**从这一次查询的结果集里装配**出来的，不会再产生新的数据库往返。
3. **每层都有基础映射兜底。** `stuAndScoresAndCourse01` `extends="stuInfoBase"`、`scoreAndCourse` `extends="scoreBase"`，字段映射只写一次；最内层的 `courseBase` 则把 `cou_id` / `cou_no` / `cou_name` / `cou_cent` 四个列显式映射到 `couId` / `couNo` / `couName` / `couCent` 四个属性上。

> [!tip] 与「嵌套 select」的本质差别
> 单看 `fetchType` 是分不出来的：写法二的 `fetchType="eager"`，写法一的 `<collection>` 写的是 `fetchType="lazy"`。真正的分水岭是嵌套节点上写的是 **`resultMap`（复用已有一列映射，不额外查库）** 还是 **`select`（再发一条 SQL）**。
> - 写 `select="命名空间.方法id"` → 每条主记录一次子查询 → N+1；
> - 写 `resultMap="命名空间.resultMapId"` + 一条表连接 SQL → 一次取回 → 无 N+1。

> [!warning] 源文缺口
> 写法二用到 `stuInfoBase`、`scoreBase` 两个被 `extends` 的基础 resultMap，以及 `t_stuinfo`、`t_score`、`t_course` 的建表 SQL，源文在本节均未给出，需参考前面的关联查询篇章。这套代码使用的是 `com.zsp.mapper` 包名，与写法一的 `com.neuedu` 体系不是同一个工程，请不要把两节代码混到同一个 mapper 目录里。

## 两种写法对比

下表结论均取自源文：标题的自行标注、源文注释、以及两段代码里实际写出的标签属性。

| 对比项 | 写法一（有问题的） | 写法二（可以使用的） |
|---|---|---|
| 源文自标 | 「有问题的」 | 「可以使用的」 |
| 嵌套节点写法 | `<collection>` / `<association>` 既无 `select`，也无 `resultMap` | `<collection>` / `<association>` 均写 `resultMap="..."` |
| SQL 条数意图 | 注释写「只发出一条 sql」，但 resultMap 与 select 对不上号，无法落实 | 一条 `SELECT` + 两次 `LEFT JOIN`，一次取回 |
| `resultMap` 与 `select` 是否一致 | 不一致：定义 id 为 `readerAndHis3`，select 里写 `readerAndHis2` | 一致：`resultMap="stuAndScoresAndCourse01"` 指向已定义的映射 |
| 关联数据如何装配 | 未指明，无法装配 | 由这一条查询的结果集，经 `resultMap` 链逐层装配 |
| `fetchType` | `lazy`（collection） / `eager`（association） | 均为 `eager` |
| 是否可直接照抄 | 否，仅作反例 | 是（需补全源文未给出的基础映射与建表 SQL） |

> [!info] 关于「查询次数」栏目的口径
> 源文没有给出任何耗时、条数统计或性能基准，上表只陈述「一条 SQL」还是「再发子查询」这一结构差别，不涉及具体快慢数字。

## 易错点小结

> [!warning] `select` 与 `resultMap` 是两条不同的路
> 嵌套的 `<collection>` / `<association>` 上：
> - 写 `select` → MyBatis 会**另外执行一次查询**来取关联数据，这是 N+1 的来源；
> - 写 `resultMap` → 复用已有映射，从**当前结果集**装配，不额外查库。
>
> 两个都不写，就落到了写法一那种装配不起来的境地。

> [!warning] 表连接的列要在 SELECT 里显式列出
> 写法二的 SQL 是 `SELECT st.*,co.*,s.*`，三张表的列都被取回，`resultMap` 链才有列可用。只连接不 SELECT，关联对象的属性仍是空的。

> [!warning] `id` 与 `resultMap` 引用必须逐字一致
> 写法一的 `readerAndHis3` / `readerAndHis2` 就是活生生的例子。跨文件的 `resultMap` 引用还要带上**命名空间**（如 `com.zsp.mapper.ScoreMapper.scoreAndCourse`），只写 id 是找不到的。
